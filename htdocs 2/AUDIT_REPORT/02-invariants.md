# Accounting & Data-Integrity Invariants

These must hold at all times, in every report, every date range, every cashier filter. Each is
cross-referenced to the finding(s) in `03-findings.md` that verify or violate it.

| # | Invariant | Status |
|---|---|---|
| 1 | Gross sales − returns − discounts = net sales, in every report, date range, cashier filter. | ✅ Verified true (fixed this session, live-tested with real invoice: 290 gross, 215 returned across two partial returns, 75 net — reconciled exactly across reports/dashboard/exhibitions). |
| 2 | A partial return affects only the returned lines/quantities, at the price actually paid on that line, never the full invoice. | ✅ True — `return.php`/`processReturn()` operate strictly on `sale_item_id` + requested quantity, refund computed from that line's stored `unit_price` (the price actually charged), never the invoice total. |
| 3 | Returned quantity per line can never exceed sold quantity minus previously-returned quantity; multiple partial returns on the same invoice must be handled. | ✅ True — `getSaleItemsWithReturned()` computes `already_returned` via `SUM(return_items.quantity)` per `sale_item_id` on every request; `return.php` clamps/rejects requests exceeding the remainder. Verified live with two sequential partial returns on the same invoice. |
| 4 | Current stock for every variant = opening + receipts − sales + returns ± adjustments ± transfers, from the movement log, and must equal the stored `stock_qty`. | ❌ **Violated** — `inventory/stocktake.php` overwrites `stock_qty` with a value computed from a stale, client-submitted "system quantity" rather than the live DB value at submit time. See **F-00 (Critical)**, reproduced live. |
| 5 | Transfers between warehouse and showroom never change total stock. | ✅ True by construction — `transfer.php` writes only to `inventory_movements`, never touches `stock_qty`. (Side note: there is no per-location balance to validate a transfer against — documented limitation, not a violation of this invariant, see F-10.) |
| 6 | Cancelled invoices are excluded from sales AND their stock is restored exactly once. | ✅ True (fixed this session) — `cancel.php` now routes through the same `processReturn()` used by partial returns, which creates the `returns`/`return_items` rows and restores stock exactly once per line, idempotently guarded by the `already_returned` calculation. Previously cancel.php restored stock but never wrote a `returns` row — that divergence is now eliminated by unifying the code path. |
| 7 | Dashboard totals = report totals = sum of invoices for the same filter. Payment-method split sums to net total including after returns (refund method tracked). | ⚠️ **Partially true.** Dashboard/report totals now reconcile with each other (fixed this session). Payment-method split (cash/card/transfer) reflects the *original* amounts collected at sale time, not reduced by returns, because **the schema has no column tracking which method a refund was paid back through** — refunds are shown only as one aggregate deduction line, not netted per payment method. This is a data-model gap, not a calculation bug; flagged as **F-08**. |
| 8 | Per-cashier performance sums to the overall total. | ✅ True — cashier performance query (`dashboard/index.php`) now uses the same net-of-returns calculation as the top-level KPI; verified the two reconcile. |
| 9 | Offline invoices synced later: no duplicate invoices, no double stock deduction, correct original timestamp/cashier, correct price tier active at sale time. | ⚠️ **No duplication** confirmed (client_uid unique key + re-check before insert). **Timestamp**: uses client-supplied `created_at` for display purposes but DB `sales.created_at` is stamped at *sync* time via `DEFAULT current_timestamp()`, not the original offline sale time — see **F-03**. **Price tier**: same server-side price recomputation as online sales, but inherits the same offer-price defect as F-01 since it reuses the identical price-resolution logic. |
| 10 | The price applied is the one valid at the moment of sale; an offer ending/starting does not change historical invoices. | ❌ **Violated, Critical** — the "moment of sale" price for `price_type='offer'` is read from the static `products.offer_price` column, which is **completely disconnected** from the time-boxed `offers` table that the cashier's screen actually uses to decide whether/what offer price to show. See **F-01**, proven with a live reproduction. |
| 11 | Cost price is never exposed to unauthorized roles (UI, API, exports, PDFs). | ❌ **Violated** — `products/create.php`, `products/edit.php`, `products/export.php` show/export `cost_price` to anyone with the `manage_products` permission, without checking the separate `view_cost` permission that exists specifically to gate this. See **F-04**. |
| 12 | Every price/stock/discount/return/cancel/offer change creates an audit-log entry (who, when, before, after). | ✅ **Largely true** — sales, returns, cancels, stock receive/transfer/adjustment, offer create/toggle, and product edits all call `logAudit()` with before/after snapshots. Minor gap: `products/edit.php`'s "new" snapshot omits `cost_price` even though the old snapshot includes it (Low severity — see F-11). |
| 13 | Money uses DECIMAL, not FLOAT; rounding is consistent, totals don't drift. | ✅ True at the schema level (`decimal(10,2)` throughout). PHP-side arithmetic uses `floatval()` for intermediate calculations before insert, which is safe for this precision/magnitude (no observed drift in testing), but is worth noting as a style risk if quantities/prices ever grow large enough for float precision loss — not a current bug. |
| 14 *(new)* | A discount applied to a sale requires the `apply_discount` permission — server-side, not just UI. | ❌ **Violated, Critical** — `pos/save_sale.php` reads `discount` directly from the POST body with **zero server-side permission check**. Any authenticated cashier can submit an arbitrary discount regardless of whether the UI exposes the field to them. See **F-12**. |
| 15 *(new)* | "Today" / date-range filters mean the business's local day (UAE, UTC+4), consistently, everywhere. | ❌ **Violated, Critical** — no `date_default_timezone_set()` anywhere in the app; PHP's default resolved to `Europe/Berlin` and MySQL's session timezone resolved to `SYSTEM` — on this very machine the two clocks are **9 hours apart from each other**, and neither is UAE time. See **F-02**. |
| 16 *(new)* | A cashier can only view/print their own invoices (consistent with the existing rule that they can only cancel/return their own). | ❌ **Violated** — `sales/invoice.php` has no ownership check; `sales/return.php`, `sales/cancel.php`, and `sales/get_sale_json.php` all enforce it. See **F-13**. |
